# 플래너 표시 및 접근권한 장애 조사 — 2026-10-12

## 조사 결론과 한계

코드와 배포 홈페이지에서 장애를 일으킬 수 있는 동작을 확인했다. 특정 사용자의 실제 사고 원인은 해당 사용자의 로그인 이메일, 오류 문구, 발생 시각과 운영 DB 기록을 대조해야 확정할 수 있다. 현재는 해당 사용자의 인증 세션이나 DB 관리자 연결이 없어 데이터가 실제 삭제됐는지는 확인하지 않았다.

확인된 재현 경로는 세 가지다: 다른 기기의 로그아웃으로 세션을 잃음, 공유 권한 상실 후 빈 개인 공간으로 전환됨, 보조 테이블 조회 실패로 정상적인 계획까지 표시하지 못함. 공유 이메일 변경으로 접근이 사라지는 경로도 로컬 PostgreSQL에서 확인했다.

## 확인한 근거

### 1. 한 기기의 로그아웃이 다른 기기 세션에도 영향을 준다

`src/Account.tsx:90`은 `supabase.auth.signOut()`을 옵션 없이 호출한다. 설치된 SDK와 [공식 문서](https://supabase.com/docs/reference/javascript/auth-signout)에서 기본 범위는 `global`이다. 로컬 브라우저에서도 `/auth/v1/logout?scope=global` 요청을 확인했다. 배포된 JS에도 동일한 호출이 존재한다.

같은 계정으로 휴대폰과 PC를 사용하다 휴대폰에서 로그아웃하면 PC의 갱신 세션까지 취소될 수 있다. PC의 기존 access token은 만료 전까지 작동할 수 있어, 잠시 뒤에 문제가 나타날 수 있다. 다른 사람의 별도 계정까지 로그아웃시키는 동작은 아니다.

세션을 잃으면 `src/planner.ts`의 인증 처리에서 화면의 공유 데이터와 공간을 비우고 편집을 잠근다. 이 처리는 DB의 계획을 삭제하지 않는다. 현재 화면은 이 상황에 대한 구체적인 이유를 안내하지 않는다.

**해결 제안:** 일반 로그아웃은 `supabase.auth.signOut({ scope: 'local' })`로 바꾸고, 모든 기기 로그아웃은 별도 명시적인 동작으로 제공한다. 예기치 않은 세션 종료에는 재로그인 안내를 표시한다. 확인된 로그아웃 범위는 사고 원인 후보이며, 실제 사용자에게 다른 기기 로그아웃이 있었는지는 아직 확인되지 않았다.

### 2. 공유 권한을 잃으면 계획이 남아 있어도 화면에서 사라진다

`supabase/schema.sql`의 `private.is_workspace_member()`는 공유 참여자를 `workspace_members.email = lower(auth.users.email)`과 이메일 확인 여부로 판별한다. 공유 참여자의 이메일 변경, 다른 이메일 계정 로그인, 관리자의 승인 삭제로 조회 권한이 사라질 수 있다. 소유자 권한은 `owner_id = auth.uid()`로 판별하므로 같은 UUID의 소유자는 이메일만 변경해도 소유권을 잃지 않는다.

Supabase RLS는 허용되지 않은 SELECT 행을 빈 결과로 반환할 수 있다. [공식 설명](https://supabase.com/docs/guides/troubleshooting/why-is-my-select-returning-an-empty-data-array-and-i-have-data-in-the-table-xvOPgx)도 이 경우를 설명한다. 빈 조회 결과만으로 실제 삭제를 판단하면 안 된다.

`src/planner.ts`의 `refresh()`는 선택했던 공간이 조회 목록에서 사라지면 본인 공간 또는 목록 첫 공간으로 바꾸고, 성공 처리에서 오류를 비운다. 브라우저 테스트에서는 공유 승인을 해제했을 때 약 5초 주기의 접근 확인 후 빈 개인 공간으로 전환되었고, 원래 계획 데이터는 테스트 서버에 남아 있었다. 화면에는 권한 상실 알림이 표시되지 않았다.

**즉시 복구:** 같은 계정인지 확인하고, 공유 공간 소유자가 현재 로그인 이메일을 다시 승인한다. 본인 소유 공간이라면 기존 `owner_id`와 현재 계정 UUID를 대조한다. 같은 이메일로 계정을 새로 만들었다는 이유만으로 기존 UUID의 소유권을 자동 이전하지 않는다.

**재발 방지:** 승인 이메일은 초대용으로 두고, 초대 수락 후 확인된 사용자 UUID를 별도 `user_id`에 연결한다. 이미 수락된 권한은 UUID로 검사하고, 이메일 조건은 아직 수락되지 않은 초대에만 사용한다. 기존 승인 전환은 대상 계정의 이메일 확인과 운영 데이터 검증을 거쳐야 한다. 마지막 공간 접근 상실 시 사용자에게 공간 이름과 재승인 절차를 안내한다. 권한이 실제 사라졌을 때 이전 공간 데이터는 화면에서 계속 노출하지 않는다.

### 3. 보조 조회 실패가 전체 플래너 로딩 실패로 이어진다

`refresh()`는 개인 공간 준비 RPC, 공간 목록, 변경 번호를 조회한 뒤 계획·완료·회원·기록·첨부를 함께 읽는다. 기록이나 첨부 조회 하나만 실패해도 `Promise.all()` 전체가 실패하고 새 공간과 계획을 화면에 반영하지 못한다. 첫 로그인 직후라면 DB의 계획이 존재해도 빈 화면과 “내 공간을 아직 불러오지 못했어요” 안내가 나타난다. 이때 `canWrite`도 false가 되어 편집이 잠긴다.

로컬 브라우저에서 `task_notes` 조회에 403/42501 응답을 넣었을 때, 계획 조회 자체가 성공했어도 계획을 표시하지 못했다. 실패 원인을 제거한 뒤 온라인 복귀와 타이머를 진행해도 자동 복구되지 않았고, 수동 “공유 기록 새로고침” 후 정상 표시됐다.

초기 로딩 실패로 `workspace`가 null이면 동기화 effect가 시작되지 않는다. 같은 계정의 `SIGNED_IN`이나 `TOKEN_REFRESHED`도 초기 데이터 재조회로 연결되지 않아 수동 새로고침이 필요할 수 있다. SDK가 재시도하는 일시적인 503 응답 한 번으로는 같은 장애가 재현되지 않았으므로, 모든 짧은 통신 오류가 즉시 이 문제를 일으킨다고 판단하지 않는다.

**즉시 복구:** 오류 문구와 Network 응답에서 실패한 테이블·함수를 확인하고 해당 권한 또는 SQL 업그레이드를 고친 뒤 수동으로 공유 기록을 새로 읽는다.

**재발 방지:** 세션은 유효하지만 공간 초기화에 실패한 경우 제한적인 자동 재시도를 둔다. 핵심 조회와 보조 조회를 구분하고 보조 기록은 실패 상태를 명시한다. 읽지 못한 첨부 목록을 단순한 빈 목록으로 처리해 삭제 기능에 넘기지 않는다. 인증 만료·권한 거부·필수 SQL 누락·통신 오류를 구분해 안내하고, 로그에는 단계·테이블·오류 코드만 남기며 토큰과 비밀번호는 남기지 않는다.

## 운영 홈페이지에서 읽기 전용으로 확인한 사항

- GitHub Pages 홈페이지와 JS 파일을 정상적으로 가져왔다.
- 배포된 JS의 Supabase 프로젝트 URL과 공개 키가 로컬 설정과 같았다. 다른 프로젝트로 연결된 정황은 발견하지 못했다.
- `workspaces`, `workspace_members`, `tasks`, `task_notes`, `task_attachments`, `workspace_activity`에 로그인 없이 조회했을 때 각각 401/42501 `permission denied for table ...`을 반환했다. 비로그인 차단이며, 피해 사용자의 인증된 권한 상태를 보여주는 결과는 아니다.
- 이메일 로그인이 활성화되어 있고 이메일 확인을 요구한다.
- 운영 데이터 변경, 사용자 가입, 로그인, 권한 변경, 배포는 수행하지 않았다. 공개 API 검사만으로 authenticated 권한과 RPC 설치 상태 전체를 확인할 수는 없다.

## 사고 사용자에 대한 확정 진단 절차

1. 사용자의 로그인 이메일, 오류 문구, 발생 시각, 본인 소유/공유 여부를 확보한다. 비밀번호와 access/refresh token은 받지 않는다.
2. `supabase/diagnostics/planner_access.sql`의 `affected@example.com`을 실제 이메일로 바꾸고 해당 Supabase 프로젝트 SQL Editor의 관리자 연결에서 실행한다. 이 파일은 읽기 전용 트랜잭션이다.
3. DB 관리자에게는 계획이 존재하는데 사용자 조회만 비어 있다면 계정 UUID·소유자·승인 이메일·이메일 확인·배포 RLS를 비교한다. 사용자가 소유하거나 작성한 공간 외의 기존 공유 공간은 사고 당시 공간 ID로 추가 확인해야 한다. 승인 행이 이미 삭제된 경우 이 진단의 공간 목록에 나타나지 않을 수 있다.
4. 사용자 브라우저에서 `/auth/v1/token`과 `/rest/v1/...` 응답을 확인한다. 세션 갱신 오류가 있으면 Authentication 로그와 다른 기기 로그아웃 여부를 대조한다. 42501만으로 세션 만료를 단정하지 않는다.
5. 운영 DB에서도 해당 계획이 없다면 이동된 공간과 삭제 여부를 별도로 확인한다. DB 백업/보존된 로그가 필요하며, 코드 검사만으로 삭제 행을 복원할 수는 없다.

## 검증

- 기존 `npm test`: 7개 파일, 39개 테스트 통과.
- `npm run build`: TypeScript 검사와 배포 빌드 통과. 로컬 JS 파일 이름은 운영과 동일한 `index-BCKFhYIl.js`였다.
- `.local/planner-access-diagnostic.spec.ts`: 3개 테스트 통과. 로그아웃 요청 범위, 보조 테이블 거부 후 수동 복구, 공유 승인 해제 후 무알림 공간 전환을 검증한다. 테스트는 모의 API를 사용하며 운영 데이터에 쓰지 않는다.
- 실제 저장소 SQL을 PGlite에 실행해, 공유 참여자의 이메일 변경 후 공간·계획 조회가 0건이 되지만 관리자 조회에는 계획이 남고, 소유자의 이메일 변경은 소유권을 제거하지 않음을 확인했다.

위 내용은 최초 조사 시점의 기록이다. 후속 수정에서 일반 로그아웃을 현재 기기로 제한하고, 부분 조회 실패 처리와 초기 로딩 재시도, 접근 상실 안내, 불완전한 기록의 수정·삭제·백업 차단을 구현했다. `tests/e2e/access-recovery.spec.ts`가 관련 회귀 테스트다.

운영 권한 변경 파일은 `supabase/migrations/20261012_stable_workspace_members.sql`이다. 기존 승인 중 확인된 이메일을 계정 UUID에 연결하며, 해제된 승인을 임의 복구하거나 소유권을 변경하지 않는다. `tests/stable-memberships.test.ts`에서 반복 실행, 이메일 변경, 다른 계정의 기존 이메일 재사용, 미인증 차단, 승인 해제 후 차단을 검증한다. 실제 운영 적용 여부는 배포·운영 작업 완료 기록과 별도로 확인해야 한다.

후속 검증: 단위·DB 테스트 44개 통과. 브라우저 검사 48개를 실행하고, 발견된 접근 안내 유지 및 복제 실패 시 입력 날짜 초기화 문제를 수정한 뒤 관련 10개 테스트를 재검증했다. 기존 1366px 화면의 문구 대비 문제는 배경 없이 글자색만 조정했으며 세 화면 크기의 레이아웃 검사를 통과했다. 개인 공간에 계획이 없고 공유 공간에 계획이 남아 있는 경우에도, 공유 계획이 누락된 개인 계획과 같은 것인지는 제목·작성자·시점을 대조해야 한다. 공유 데이터 존재만으로 개인 데이터 삭제 여부를 단정하지 않는다.

別 계정의 개인 공간 격리도 추가 검증했다. 계정 A가 자신의 공간에 만든 계획을 계정 B로 조회·수정·삭제하려고 시도해 모두 거부되며, 계정 A로 다시 조회하면 원본이 유지된다. 단위·DB 테스트는 총 45개 통과했다. 이는 저장소 SQL에 대한 검사이며, 운영 DB의 다른 정책·트리거·관리자 작업까지 없음을 증명하지 않는다. 운영 설정 확인에는 `supabase/diagnostics/planner_deletion_paths.sql`을 사용한다. 기존 앱은 삭제 행 자체나 삭제 주체의 이력을 별도 보존하지 않으므로 과거 누락 원인 확정에는 운영 API/DB 로그 또는 백업이 필요하다.
