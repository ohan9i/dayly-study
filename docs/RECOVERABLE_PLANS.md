# 복구 가능한 계획 삭제와 공간 이동

2026-10-17 조사에서 사라진 다섯 계획은 서버의 `task_deletion_history`에 실제 삭제로 기록되어 있었습니다. 다섯 건 모두 같은 인증 계정으로 2026-10-17 00:29:42~57 KST에 삭제됐고, Supabase API Gateway에는 Windows Whale 브라우저에서 `prepare_task_deletion`과 `delete_task_with_history` 요청이 성공한 기록이 있습니다. 날짜가 이틀 지났다는 이유로 자동 삭제하는 코드나 데이터베이스 예약 작업은 발견되지 않았습니다. 서버 로그는 로그인 계정과 클라이언트 종류를 보여주지만 실제 조작한 사람을 확정하지는 못합니다.

해당 다섯 계획은 삭제 이력의 원본 스냅샷에서 같은 ID·작성자·날짜·공간으로 복원했습니다. 저장돼 있던 완료 표시 두 건도 복원했습니다. 이 작업은 운영자가 서버에서 수행했고 변경 이력에는 서버 관리 작업으로 남습니다.

## 새 동작

- 확인된 공간 참여자는 해당 공간의 계획을 휴지통으로 보내거나 복원할 수 있습니다. 작성자가 달라도 가능합니다.
- 계획을 다른 공간으로 옮기려면 두 공간 모두의 확인된 참여자여야 합니다. 계획 ID, 작성자, 날짜, 수행 기록, 완료 상태와 첨부 원본은 유지됩니다.
- 휴지통 삭제는 `tasks.deleted_at/deleted_by`만 기록하며 하위 기록과 Storage 원본을 지우지 않습니다. 일반 목록의 RLS는 휴지통 계획을 숨깁니다.
- 물리적 계획 삭제, 공간 삭제, 완료된 첨부 원본 삭제는 서버에서 계속 차단합니다. 따라서 실수로 누른 삭제를 설정의 휴지통에서 되돌릴 수 있습니다.
- `task_change_history`에 생성, 수정, 날짜 변경, 공간 이동, 휴지통 삭제와 복원 전후의 내용을 남깁니다. 승인된 참여자는 해당 공간의 이력을 읽지만 브라우저에서 이력을 고칠 수 없습니다.
- 이전 버전에서 이미 물리적으로 삭제한 계획은 서버 삭제 이력의 스냅샷과 원본 첨부가 있을 때 복원할 수 있습니다. 원본 첨부가 사라졌다면 암호화 백업에서 먼저 복원해야 합니다.
- 이전 앱의 삭제 API도 휴지통 삭제로 바뀌며 첨부 원본 목록을 반환하지 않습니다. 따라서 오래된 브라우저 탭도 원본을 먼저 지우지 않습니다.

## 설치와 확인

기존 마이그레이션을 적용한 뒤 `supabase/migrations/20261017_permanent_planner_retention.sql`, 마지막으로 `supabase/migrations/20261017_recoverable_member_actions.sql`을 실행합니다. 마지막 파일은 반복 실행할 수 있습니다. 설정의 **기록 보호**에 `복구 보호 적용됨`이 보이면 서버 트리거를 확인한 것입니다.

`npm test`의 `recoverable-member-actions.test.ts`는 승인된 다른 작성자의 계획 이동, 삭제·복원, 첨부와 수행 기록 보존, 미승인 계정 거부, 옛 앱 호환, 날짜 변경 이력과 백업 포함 여부를 검사합니다. 실제 운영 데이터의 복원과 서버 적용 결과는 별도로 확인해야 합니다.

정기 백업에는 새 변경 이력도 포함됩니다. 백업은 하루에 한 번 실행되므로 마지막 성공 시각과 GitHub Actions의 실행 결과를 함께 확인합니다. [백업·복구 안내](DATA_PROTECTION.md)
