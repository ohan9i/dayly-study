# 저장된 플래너 삭제 방지 (2026-10-17)

## 확인된 원인과 운영 서버 증거

Supabase 운영 프로젝트에서 직접 조회했다. 적용 전 계획은 32개, 공간은 2개였다. 공간별 계획은 30개(다른 사람이 작성한 계획 21개), 2개(다른 사람이 작성한 계획 1개)였다. 서버의 `tasks_remove`, `notes_remove` 정책은 작성자 또는 공간 소유자의 삭제를 허용했다. `move_task`도 작성자가 다른 공간으로 옮길 수 있어, 원래 공간의 목록에서 사라질 수 있었다.

삭제 이력에는 2026-10-17 **00:29:42~00:29:57 한국 시간**에 작성자 계정으로 실행된 계획 삭제 5건이 있었다. 이는 인증된 계정의 삭제 요청이 실행된 증거이며, Supabase의 자동 데이터 소실을 입증하는 기록은 아니다. 이력이 설치되기 전의 삭제나 개별 사용자의 모든 소실 사례까지 이 결과로 설명할 수는 없다. 기록된 5건은 현재 계획 2개가 있는 공간의 항목이었다. 의도적인 정리였을 수도 있어 자동 복원하지 않았다.

기존 삭제 과정은 Storage 원본 삭제 → 첨부 메타데이터 삭제 → 계획 삭제 순서였다. 마지막 요청이 실패하면 앞 단계 파일만 삭제될 수 있었다. 삭제 이력에는 파일 목록이 있지만 파일 바이트는 없으므로 이력만으로 원본 파일을 복구할 수 없다.

점검 시 `private.planner_backup_runs`의 마지막 성공 시각은 **NULL**이었다. 예약 워크플로 파일이 존재하는 것과 백업 성공은 다르다. GitHub 서버용 키와 백업 활성화 설정은 [DATA_PROTECTION.md](DATA_PROTECTION.md)를 따른다. 성공하지 않은 백업을 실행 중이라고 표현하지 않는다.

추가 점검에서 `DAYLY_BACKUPS_ENABLED`가 없었고, 기존 `SUPABASE_BACKUP_SECRET_KEY`는 백업 도구의 서버 키 검사에서 거부되는 값이었다. 사용자의 승인을 받아 Supabase의 기존 서버용 키를 GitHub의 해당 Secret에 등록했다. [암호화 백업 실행](https://github.com/ohan9i/dayly-study/actions/runs/38985896460)이 파일 업로드와 서버 성공 기록까지 완료된 뒤 `DAYLY_BACKUPS_ENABLED=true`를 설정했다. 매일 03:00 한국 시간에 예약되며 실행 시각은 GitHub 대기로 지연될 수 있다. Artifact 보관은 30일이다.

생성된 암호화 백업을 내려받아 기존 Windows 보호 복구 키로 **실제 복호화와 파일 무결성 검사**를 완료했다. 복구본에는 계획 32개와 첨부 원본 17개가 들어 있다. 복구 확인 폴더는 `.local/retention-restore-38985896460`이며 Git에서 제외된다. 운영 데이터베이스로 복구본을 덮어쓰지 않았다. 이 과정에서 Windows PowerShell 보안 모듈 자동 로딩에 의존하던 복구 도구를 명시적인 모듈 로딩으로 수정했다.

## 변경된 동작

- 저장된 계획과 수행 기록은 작성자·공간 소유자 모두 삭제할 수 없다.
- 계획의 ID·작성자·공간을 고정한다. 작성자가 참여를 그만두거나 공유 승인이 해제되어도 계획은 원래 공간에 남고 소유자는 계속 볼 수 있다. 승인이 해제된 참여자의 읽기 권한은 다시 부여하지 않는다.
- 제목·날짜·세부 항목·수행 내용 편집과 완료 체크는 기존 권한대로 가능하다. 이 기능은 편집 이력/버전 복원 기능이 아니다.
- 업로드가 완료된 첨부는 삭제·교체·미완료 상태로 되돌리기를 차단한다. 실패한 업로드(`pending`)만 기존 소유권 검사 후 정리할 수 있다.
- 삭제·공간 이동 버튼을 제거한다. 예전 컴포넌트 호출도 클라이언트 함수에서 거부한다. 예전 배포본의 삭제 준비 RPC와 이동 RPC도 서버에서 거부한다.
- 설정의 기록 보호는 `get_planner_retention_status()`로 실제 트리거 활성 상태를 확인한다. RPC가 없거나 보호가 꺼져 있으면 경고한다.

서버에서는 삭제 권한 회수, 행 트리거, TRUNCATE 방지, Storage 제한 정책과 원본 경로 보호 트리거를 함께 사용한다. RLS를 우회하는 기존 `SECURITY DEFINER` 함수나 계정·공간 연쇄 삭제도 행 트리거에서 막는다. [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security), [연쇄 삭제](https://supabase.com/docs/guides/database/postgres/cascade-deletes)

## 설치와 검증

기존 migration 뒤에 `supabase/migrations/20261017_permanent_planner_retention.sql`을 **마지막으로** 실행한다. 반복 실행 가능하며 트랜잭션으로 적용한다. 기존 계획·수행 기록·파일을 삭제하거나 이동하지 않는다. 이전 migration을 재실행했으면 이 파일도 마지막에 다시 실행한다. 새 프로젝트에도 같은 순서가 필요하다.

운영 서버에는 2026-10-17 이 migration과 동일한 정의를 적용했다. 적용 후 계획 **32개 유지**, 활성 보호 트리거 **9개**, Storage 제한 정책 **2개**, 브라우저 계정의 계획·수행 기록 DELETE 권한 **없음**을 확인했다.

로컬 단위/SQL 테스트 61개, 변경 관련 브라우저 시나리오 26개와 배포 빌드를 통과했다. 첨부 상태 저장은 성공했지만 응답만 실패한 경우에도 원본을 정리하지 않는 시나리오를 추가했고, 변경된 첨부·보호 화면 테스트 8개를 다시 통과했다. Windows 샌드박스의 기본 임시 폴더에서는 파일 rename과 Vitest 캐시 접근 오류가 있어, 임시 폴더를 `.local/test-temp`로 지정해 단위 테스트를 실행했다. 브라우저 테스트는 로컬 서버 통신이 가능한 실행 환경에서 테스트 API로 검사했다.

`tests/permanent-retention.test.ts`는 실제 PostgreSQL 엔진(PGlite)에서 작성자·소유자 삭제, 기존 삭제 RPC, 이동, 직접 관리자 DELETE, TRUNCATE, 계정 연쇄 삭제, 파일 원본 삭제, `ready`→`pending` 우회, 실패한 업로드 정리, 승인 해제 후 소유자 조회, 트리거 비활성 감지를 검사한다. 기존 migration만 사용하는 테스트는 예전 동작에서 업그레이드하기 위한 회귀 검증이다.

## 보장 범위

앱과 정상 서버 접근에서 저장된 데이터가 삭제되거나 공간 이동으로 사라지는 것을 막는다. 데이터베이스 최고 관리자가 보호 트리거를 해제하거나 테이블·프로젝트 자체를 없애는 작업, 플랫폼 장애, 별도 저장소 관리자 작업까지 영구 보존을 보장하지는 않는다. 이 범위에는 독립적인 성공 백업이 필요하다. 파일 업로드가 완료되기 전의 `pending` 상태는 보존 확정 상태가 아니다.
